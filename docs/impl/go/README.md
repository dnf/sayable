# Go Style Guide

Style conventions for Go implementations in this project.
Assumes familiarity with Go; links to canonical references where appropriate
rather than re-explaining language fundamentals.

## 1. Project Conventions

These conventions are specific to this project and take precedence over
general Go advice.

### Zero Dependencies

This project permits zero runtime dependencies. This means:

- No `testify`, `go-cmp`, or any testing library. Use the standard `testing`
  package with explicit comparisons.
- No `strconv` if a simpler hand-rolled conversion suffices (the project uses
  a custom `itoa` to avoid importing `strconv` for a single function).
- No logging library. Errors are returned, not logged.

### Nullable Returns with `*string`

Public API methods that can fail (invalid input, future date) return `*string`
rather than `(string, error)` or `(string, bool)`. This is a deliberate
design choice for API consistency across 29 language implementations, some of
which lack Go's multiple-return-value idiom. A `nil` return means "no valid
result."

### Optional Parameters with Variadic Strings

The project uses `...string` for optional parameters (`asOf`, `gender`):

```go
func (pt *SayableAge) FormatAge(dateOfBirth string, asOf ...string) *string
func (pt *SayableAge) FormatStage(dateOfBirth string, opts ...string) *string
```

This trades Go's type safety for cross-language API consistency. Within this
project, accept the pattern. In general Go code, prefer distinct parameters,
a config struct, or functional options.

### External Test Package

Tests use `package sayableage_test` (black-box testing), not
`package sayableage`. This tests the public API surface only. When internal
functions must be tested, use the `export_test.go` pattern:

```go
// export_test.go (in package sayableage, not sayableage_test)
package sayableage

// SetTimeNow exposes timeNow for testing.
func SetTimeNow(f func() time.Time) { timeNow = f }
func RestoreTimeNow()               { timeNow = time.Now }
```

### Test ID Annotations

Every test case must carry a comment with its canonical test ID from
`age/config/tests.json`:

```go
assertAge(t, "born today", pt.FormatAge("2025-06-15", "2025-06-15"), "Newborn") // 2.1
```

### Generated Locale Files

Files in `locales/` are generated by the codegen system. Never edit them by
hand. Run `just generate locales` to regenerate.

## 2. Naming Conventions

Go naming is one of the most distinctive aspects of the language. The case of
the first letter determines visibility.

### Packages

Package names are lowercase, single-word, no underscores, no mixedCaps:

```go
package strconv   // good
package httputil  // good

package str_conv  // bad -- no underscores
package myPackage // bad -- no mixedCaps
```

The package name is part of every qualified reference, so avoid stutter:

```go
// In package http:
http.Server     // good -- reads naturally
http.HTTPServer // bad -- "HTTP" already implied by package name
```

Avoid meaningless package names like `util`, `common`, `misc`, and `helpers`.
These names convey nothing and invite dumping unrelated code together.

Names like `types`, `models`, and `api` are acceptable when the package
genuinely serves that focused purpose (the standard library has `go/types`),
but do not use them as catch-all dumping grounds.

### Exported vs. Unexported

Uppercase first letter exports. Lowercase keeps it package-private.

Start unexported. Export only what callers need. Unexported things can always
be exported later; removing exports is a breaking change.

### Functions, Methods, and Variables

Use MixedCaps, never underscores. Getters omit `Get` (setters keep `Set`):

```go
func (u *User) Name() string     // getter -- no "Get"
func (u *User) SetName(n string) // setter -- "Set" is fine
```

Name length is proportional to scope. Short names for tight scopes,
descriptive names for broader ones:

```go
for i, v := range items { ... }             // fine in a loop
var defaultTimeout = 30 * time.Second       // package-level, descriptive
```

Conventional short names: `r` for `io.Reader`, `w` for `io.Writer`, `ctx`
for `context.Context`, `t` for `*testing.T`, `i/j/k` for loop indices.

### Method Receivers

Use a one- or two-letter abbreviation of the type name. Be consistent across
all methods on the type. Never `this`, `self`, or `me`:

```go
func (c *Client) Do(req *Request) (*Response, error)  // good
func (self *Client) Do(req *Request) (*Response, error) // bad
```

### Constants, Initialisms, Interfaces, Errors

- Constants: MixedCaps like everything else. Never `ALL_CAPS`.
- Initialisms: all same case (`HTTPClient`, not `HttpClient`; `userID`, not `userId`).
- One-method interfaces: method name plus `-er` suffix (`Reader`, `Stringer`).
- Sentinel errors: `Err` prefix (`ErrNotFound`). Error types: `Error` suffix (`ValidationError`).

## 3. Code Formatting

### gofmt Is Non-Negotiable

All Go code must be formatted with `gofmt`. No exceptions.

> "Gofmt's style is no one's favorite, yet gofmt is everyone's favorite."
> -- Go Proverbs

Run `goimports` (a superset of `gofmt` that also manages imports) before
committing.

### Import Grouping

Three groups separated by blank lines: stdlib, external dependencies, internal
packages. `goimports` handles this automatically:

```go
import (
    "context"
    "fmt"

    "golang.org/x/sync/errgroup"

    "myproject/internal/config"
)
```

Avoid renaming imports unless there is a collision. Never use dot imports
(`. "pkg"`) in production code.

### Line Length

Go has no rigid line length limit. Do not wrap lines artificially. If a line
is too long, the real fix is usually shorter names or extracted logic:

```go
// Fine as one line
result, err := client.FetchUser(ctx, userID, WithTimeout(5*time.Second))

// If too long, extract a variable
opts := WithTimeout(5 * time.Second)
result, err := client.FetchUser(ctx, userID, opts)
```

## 4. Error Handling

Errors are values, not exceptions. Handle them explicitly.

### The Basic Pattern

Check errors immediately. Return early. Happy path at minimal indentation:

```go
f, err := os.Open(filename)
if err != nil {
    return fmt.Errorf("opening config: %w", err)
}
defer f.Close()
```

### Error Strings

Lowercase (unless starting with a proper noun or acronym), no trailing
punctuation:

```go
fmt.Errorf("opening file: %w", err)       // good
fmt.Errorf("Opening file: %w.", err)       // bad
```

### Wrapping with %w and %v

Use `%w` when callers should be able to inspect the cause with `errors.Is` or
`errors.As`. Use `%v` to add context while intentionally hiding the
underlying error:

```go
return fmt.Errorf("user lookup: %w", err)  // callers can unwrap
return fmt.Errorf("user lookup: %v", err)  // opaque -- callers cannot unwrap
```

Since Go 1.20, `fmt.Errorf` supports multiple `%w` verbs for wrapping
multiple errors. Use this when aggregating errors from concurrent operations:

```go
return fmt.Errorf("batch failed: %w and %w", err1, err2)
```

### Handle Errors Once

Either log or return. Never both:

```go
// Good -- return with context
if err != nil {
    return fmt.Errorf("connecting to db: %w", err)
}

// Good -- log and degrade
if err != nil {
    log.Printf("connecting to db: %v", err)
    return fallbackValue, nil
}

// Bad -- log AND return creates duplicate log entries
if err != nil {
    log.Printf("connecting to db: %v", err)
    return fmt.Errorf("connecting to db: %w", err)
}
```

### Do Not Ignore Actionable Errors

Always handle errors from operations where failure is actionable. The
common exceptions:

- `bytes.Buffer.Write` (documented as never failing)
- `Close` on read-only file descriptors (failure is non-actionable; data was
  already consumed)

For write paths, always check `Close` errors -- a `Close` failure can mean
unflushed data:

```go
// Write path -- must check Close
if err := f.Close(); err != nil {
    return fmt.Errorf("closing output: %w", err)
}
```

### Do Not Panic

`panic` is not for normal error handling. Use it only for genuinely
unrecoverable programmer errors (invariant violations). Return errors instead.

`Must*` functions that panic are acceptable only for program initialization
at package level:

```go
var defaultConfig = MustParse("default.yaml")
```

## 5. Interfaces

### Keep Interfaces Small

> "The bigger the interface, the weaker the abstraction." -- Go Proverbs

One- or two-method interfaces are the sweet spot.

### Accept Interfaces, Return Structs

Functions should accept interfaces (flexibility) and return concrete types
(full access):

```go
func NewDecoder(r io.Reader) *Decoder { ... }  // good
func NewDecoder(r io.Reader) Decoder { ... }   // bad -- returns interface
```

### Define Interfaces at the Consumer

Interfaces belong in the package that *uses* them, not the one that
*implements* them. This allows each consumer to define the minimal interface
it needs.

### When to Define Interfaces

Define an interface when it has at least one consumer that benefits from the
abstraction. Tests are legitimate consumers. Avoid defining interfaces that
have zero consumers.

```go
// Bad -- no consumer needs this abstraction yet
type UserStore interface { ... }
type userStore struct { ... }
func NewUserStore() UserStore { ... }

// Good -- just export the concrete type until something needs the interface
type UserStore struct { ... }
```

### Compile-Time Interface Compliance

Verify satisfaction at compile time using the blank identifier:

```go
var _ http.Handler = (*MyHandler)(nil)
```

## 6. Concurrency

> "Don't communicate by sharing memory; share memory by communicating."
> -- Go Proverbs

### Goroutines

Every goroutine must have a clear termination condition. Never fire-and-forget
without a shutdown mechanism:

```go
func (s *Server) Run(ctx context.Context) error {
    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case req := <-s.requests:
            s.handle(req)
        }
    }
}
```

### Channels

> "Channels orchestrate; mutexes serialize." -- Go Proverbs

Use unbuffered channels for synchronization and buffered channels for
decoupling producer/consumer rates. Choose buffer sizes deliberately: size
them based on concurrency level or batch size, not arbitrary round numbers.

```go
done := make(chan struct{})               // unbuffered -- synchronization
work := make(chan Task, runtime.NumCPU()) // buffered -- matches worker count
```

### sync Package

Use `sync.Mutex` and `sync.RWMutex` for protecting shared state. Place the
mutex above the fields it protects. Never embed a mutex in a public struct
(leaks `Lock`/`Unlock` as exported methods):

```go
type Cache struct {
    mu    sync.RWMutex   // guards items
    items map[string]Item
}
```

Use `sync.WaitGroup` to wait for multiple goroutines, `sync.Once` for
one-time initialization.

### context.Context

Pass `context.Context` as the first parameter to functions that may block or
need cancellation:

```go
func FetchUser(ctx context.Context, id string) (*User, error) { ... }
```

Prefer passing context as a function parameter. Storing context in a struct
is acceptable for request-scoped objects whose lifetime matches the context's
lifetime (like `http.Request`). Do not store context in long-lived objects
like server configs or connection pools.

Use `context.Background()` only at the top of the call tree (`main`, `init`,
`TestXxx`).

## 7. Type System

### Structs

Initialize with field names. Omit zero-value fields:

```go
srv := &http.Server{
    Addr:         ":8080",
    ReadTimeout:  5 * time.Second,
    WriteTimeout: 10 * time.Second,
}
```

### Make the Zero Value Useful

> "Make the zero value useful." -- Go Proverbs

Design types so their zero value is ready to use: `sync.Mutex` zero value is
unlocked, `bytes.Buffer` zero value is an empty buffer.

### Embedding

Do not embed types in public structs unless the promoted methods are genuinely
part of the outer type's API. Prefer explicit delegation for public types:

```go
type Server struct {
    logger *log.Logger // private -- delegate explicitly
}
```

### Type Assertions

Always use the comma-ok form to avoid panics:

```go
s, ok := val.(string)
if !ok {
    return errors.New("expected string")
}
```

### Receiver Type: Pointer vs. Value

If any method on a type requires a pointer receiver (mutation, sync.Mutex,
large struct), use pointer receivers for all methods on that type. This
ensures the method set is consistent whether the type is used as `T` or `*T`.

If no method requires a pointer receiver, value receivers are fine for small,
immutable types.

### Generics

Start with concrete types. Add generics only when you have multiple
implementations of the same algorithm with different types and the
duplication is significant:

```go
func Map[T, U any](s []T, f func(T) U) []U {
    result := make([]U, len(s))
    for i, v := range s {
        result[i] = f(v)
    }
    return result
}
```

Use generics for algorithms and data structures that genuinely operate on
multiple types. Avoid using generics solely to create framework-style
abstractions.

## 8. Testing

### Table-Driven Tests

The standard Go testing pattern. Define test cases as a slice of structs,
loop over them with `t.Run`:

```go
func TestFormatAge(t *testing.T) {
    tests := []struct {
        name string
        days int
        want string
    }{
        {name: "newborn", days: 0, want: "just born"},
        {name: "one week", days: 7, want: "1 week"},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got := FormatAge(tt.days)
            if got != tt.want {
                t.Errorf("FormatAge(%d) = %q, want %q", tt.days, got, tt.want)
            }
        })
    }
}
```

### Standard Library Only

This project uses the standard `testing` package with explicit comparisons.
No assertion libraries (zero-dependency policy). Write clear failure messages
that include function name, inputs, actual output, and expected output:

```go
t.Errorf("FormatAge(%d, %q) = %q, want %q", days, locale, got, want)
```

### Test Package Naming

Use `package foo_test` (external test package) for testing the public API.
This is the default for this project. Use `package foo` (internal test
package) only when testing unexported functions is unavoidable, and prefer
the `export_test.go` pattern to keep tests in the external package.

### Test Helpers

Mark helper functions with `t.Helper()` so failure messages point to the
calling test:

```go
func assertAge(t *testing.T, name string, got *string, want string) {
    t.Helper()
    if got == nil {
        t.Errorf("%s: got nil, want %q", name, want)
        return
    }
    if *got != want {
        t.Errorf("%s: got %q, want %q", name, *got, want)
    }
}
```

### t.Error vs. t.Fatal

Use `t.Error` (non-fatal) when subsequent checks are still meaningful. Use
`t.Fatal` only when the test cannot continue. Never call `t.Fatal` from a
goroutine.

### Example Tests

Write `Example` functions to demonstrate usage. They appear in godoc and run
as tests:

```go
func ExampleFormatAge() {
    fmt.Println(FormatAge(45))
    // Output: 6 weeks
}
```

## 9. Common Idioms

### The Blank Identifier

Use `_` to discard unwanted values, for compile-time interface checks, and
for side-effect-only imports:

```go
for _, v := range items { ... }             // discard index
var _ fmt.Stringer = (*MyType)(nil)          // compile-time check
import _ "image/png"                        // register decoder
```

### init Functions

Use sparingly. `init` runs implicitly and cannot be called directly. Prefer
explicit initialization in `main()`. Acceptable uses: registering codecs or
drivers.

Do not use `init()` for I/O operations, complex setup that can fail, spawning
goroutines, or global state mutation that callers cannot control.

### iota

The zero value of an enum type should represent the default or unset state.
Start at 0 when the first constant is a sensible default. Skip zero when an
uninitialized variable should not silently match a valid constant:

```go
// Zero is a valid default
type PluralCategory int
const (
    Zero PluralCategory = iota  // 0 -- meaningful
    One
    Two
    Few
    Many
    Other
)

// Zero should be invalid
type Color int
const (
    _ Color = iota  // skip zero
    Red
    Green
    Blue
)
```

### Optional Configuration Patterns

For constructors with optional parameters, consider these patterns in order
of simplicity:

**Config struct** -- simplest, most discoverable:

```go
type Config struct {
    Port    int
    Timeout time.Duration
}

func NewServer(addr string, cfg Config) *Server { ... }
```

**Functional options** -- when you need validation, private fields, or
open extension:

```go
type Option func(*Server)

func WithPort(port int) Option { ... }

func NewServer(addr string, opts ...Option) *Server { ... }
```

Prefer the simpler pattern that meets your requirements.

### defer

Use `defer` for cleanup. Defer after the error check, not before:

```go
f, err := os.Open(path)
if err != nil {
    return err
}
defer f.Close()
```

### Defensive Copying

For public APIs of mutable objects that store received slices or maps, copy
them to prevent callers from mutating internal state:

```go
func (s *Store) SetItems(items []Item) {
    s.items = make([]Item, len(items))
    copy(s.items, items)
}
```

For immutable data (like locale tables initialized once and never modified)
or internal package boundaries, copying adds cost without benefit.

### Nil Slices

A nil slice and an empty slice behave identically for `len`, `cap`, `append`,
and `range`. Prefer `var s []string` (nil) over `s := []string{}` (empty).

Exception: JSON encoding. Nil slices encode as `null`, empty slices as `[]`.

### Time Handling

Use `time.Time` for instants and `time.Duration` for periods. Never raw
integers for time:

```go
func Poll(interval time.Duration) { ... }  // good
func Poll(intervalMS int) { ... }          // bad
```

## 10. Things to Avoid

### Naked Returns

Name return values for documentation when it improves clarity. Always use
explicit return statements; never use bare `return`. Named returns without
explicit values obscure what is being returned and scale poorly as functions
grow.

### Interface Pollution

Do not define interfaces with zero consumers. An interface needs at least one
concrete consumer (production code or tests) that benefits from the
abstraction before it earns its place.

### Mutable Global State

Avoid package-level mutable variables. They make code hard to test and create
hidden dependencies. Inject dependencies instead:

```go
// Bad -- global state
var db *sql.DB

// Good -- injected dependency
type UserStore struct {
    db *sql.DB
}
```

The one acceptable exception in this project is `timeNow` -- a package-level
`var` that enables deterministic testing by replacing `time.Now`.

### os.Exit Outside of main

Call `os.Exit` or `log.Fatal` only in `main()`. Everywhere else, return
errors.

### In-Band Error Values

Do not use sentinel return values (-1, "", nil) to signal errors. Use Go's
multiple return values or, where cross-language API consistency requires it,
this project's `*string` nil-return pattern.

### Embedding sync.Mutex in Public Structs

Never embed `sync.Mutex` in a public struct. It exposes `Lock` and `Unlock`
as exported methods. Use an unexported field:

```go
type Cache struct {
    mu    sync.Mutex     // unexported -- not part of public API
    items map[string]Item
}
```

## 11. Tooling

### Required Tools

```sh
goimports -l .          # check formatting (superset of gofmt)
go build ./...          # compilation check
go vet ./...            # built-in static analysis (zero false positives by design)
go test -race ./...     # tests with race detection
```

### Recommended Additional Tools

- **staticcheck** ([staticcheck.dev](https://staticcheck.dev)) -- advanced
  static analysis for bugs, performance, and style
- **golangci-lint** ([golangci-lint.run](https://golangci-lint.run)) --
  meta-linter running many linters in parallel. Use the default linter set;
  disable specific linters only with documented justification.
- **govulncheck** ([pkg.go.dev](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck))
  -- vulnerability scanner that reports only vulnerabilities in code paths
  actually called

### Recommended CI Pipeline

```sh
goimports -l .                                        # formatting
go build ./...                                        # compilation
go vet ./...                                          # built-in checks
staticcheck ./...                                     # static analysis
go test -race ./...                                   # tests + race detection
go mod tidy && git diff --exit-code go.mod go.sum     # dependency hygiene
govulncheck ./...                                     # vulnerability scan
```

### go test -race

The race detector finds data races at runtime. Essential for any code using
goroutines. A race found by the detector is always a real bug. Run it in CI.
